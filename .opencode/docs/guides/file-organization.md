# File Organization Guide

This guide explains where to place different types of files when working on site-nine as an agent.

## Golden Rule: Don't Pollute the Project Root

**⚠️ CRITICAL: Never create temporary or work-in-progress files in the project root or main source directories.**

All agent work artifacts belong in `.opencode/work/`. The project root and source directories should only contain:
- Production code
- Configuration files
- Documentation that ships with the project
- Standard project files (README.md, LICENSE, etc.)

## Directory Structure Overview

```
.opencode/
├── commands/          # OpenCode slash commands
├── data/              # Reference documentation and system data
├── docs/              # Project documentation
│   ├── adrs/         # Architecture Decision Records
│   ├── architecture/ # Architecture documentation
│   ├── guides/       # How-to guides (like this one)
│   └── roles/        # Agent role definitions
├── skills/            # OpenCode skill definitions
├── scripts/           # Permanent utility scripts
└── work/              # 🎯 All agent work artifacts go here!
    ├── epics/        # Epic planning and tracking
    ├── handoffs/     # Work handoff documentation
    ├── missions/     # Mission logs (one per agent session)
    ├── planning/     # General planning documents
    ├── scripts/      # Temporary task-specific scripts
    ├── sessions/     # OpenCode session tracking
    ├── tasks/        # Individual task files
    └── test-plans/   # Test planning documents
```

## The .opencode/work/ Directory

**This is YOUR workspace.** All files you create during missions belong here.

### work/missions/

**Purpose:** Mission logs documenting your work session.

**File naming:** Auto-generated by `s9 mission start`:
```
YYYY-MM-DD.HH:MM:SS.role.persona.codename.md
```

**Example:**
```
2026-02-12.23:55:17.documentarian.jibril.gamma-raven.md
```

**What goes here:**
- Work log entries
- Decisions made during the mission
- Files created/modified
- Blockers encountered
- Key learnings

**When to update:**
- Throughout your mission (it's a living document!)
- After completing significant tasks
- When making important decisions
- When encountering/resolving blockers

**See also:** Step 4.5 in the session-start skill for mission file maintenance guidelines.

### work/tasks/

**Purpose:** Individual task tracking files.

**File naming:** Auto-generated by `s9 task create`:
```
TASK-ID.md
```

**Example:**
```
DOC-H-0121.md
```

**What goes here:**
- Task description and requirements
- Status updates
- Progress notes
- Time tracking

**When to update:**
- Via `s9 task update` command
- Automatically updated by task management commands

**Note:** You typically don't edit these files directly - use the `s9 task` commands instead.

### work/scripts/

**Purpose:** Temporary, task-specific scripts.

**File naming:**
```
TASK-ID-descriptive-name.ext
```

**Examples:**
```
OPR-H-0116-migrate-task-status.py
DOC-H-0118-audit-cli-commands.sh
```

**What goes here:**
- One-time migration scripts
- Testing utilities
- Problem-solving scripts
- Task-specific automation

**What does NOT go here:**
- Permanent project utilities (use `scripts/` in project root)
- Production code
- Reusable tools

**Requirements:**
- Must include task ID in filename
- Must have header with task ID, mission ID, purpose, and deletion criteria
- Must be cleaned up when task/mission completes

**See also:** `.opencode/work/scripts/README.md` for detailed guidelines.

### work/epics/

**Purpose:** Epic planning and coordination.

**File naming:** Auto-generated by `s9 epic create`:
```
EPIC-ID.md
```

**Example:**
```
EPC-H-0004.md
```

**What goes here:**
- Epic overview and goals
- Task breakdown
- Progress tracking
- Coordination notes

### work/handoffs/

**Purpose:** Work handoff documentation between agents.

**File naming:** Auto-generated by `s9 handoff create`:
```
HANDOFF-ID.md
```

**What goes here:**
- Work to be handed off
- Context and decisions
- Blockers or considerations
- References to relevant files

### work/planning/

**Purpose:** General planning documents not tied to specific tasks.

**What goes here:**
- Brainstorming documents
- Design sketches
- Investigation notes
- Proof-of-concept plans

**Note:** If your planning relates to a specific task, consider documenting it in the task file or mission log instead.

### work/sessions/

**Purpose:** OpenCode TUI session tracking.

**Managed by:** System (via `s9 mission rename-tui`)

**Do not manually create files here.**

### work/test-plans/

**Purpose:** Detailed test planning documents.

**What goes here:**
- Test strategy documents
- Test scenarios and cases
- Testing checklists
- QA planning

## Other Important Directories

### .opencode/docs/

**Purpose:** Project documentation that benefits all agents.

**What goes here:**
- Architecture documentation
- ADRs (Architecture Decision Records)
- How-to guides
- Role definitions
- System reference docs

**Subdirectories:**
- `adrs/` - Architecture decisions
- `architecture/` - System design docs
- `guides/` - How-to guides
- `roles/` - Agent role definitions

**When to add files:**
- When creating documentation for long-term use
- When documenting architecture decisions
- When writing guides for other agents

**Do NOT add:**
- Temporary notes
- Work-in-progress docs
- Mission-specific logs

### .opencode/skills/

**Purpose:** OpenCode skill definitions.

**What goes here:**
- Workflow automation skills
- Reusable agent instructions
- Multi-step procedures

**File structure:**
```
skills/
└── skill-name/
    ├── SKILL.md          # Main skill definition
    ├── scripts/          # Skill-specific scripts
    └── reference/        # Skill-specific reference data
```

**When to add files:**
- When creating new reusable workflows
- When documenting common procedures
- When building automation for agents

### .opencode/scripts/

**Purpose:** Permanent utility scripts for the project.

**What goes here:**
- Database maintenance scripts
- Development utilities
- CI/CD helpers
- Tools used repeatedly

**What does NOT go here:**
- One-time scripts (use `.opencode/work/scripts/`)
- Task-specific automation
- Temporary testing scripts

## Common File Placement Scenarios

### "I need to create a quick script for this task"

**Use:** `.opencode/work/scripts/TASK-ID-description.py`

**Example:** You're working on DOC-H-0118 and need a script to audit CLI commands:
```
.opencode/work/scripts/DOC-H-0118-audit-cli-commands.py
```

### "I want to document my work session"

**Use:** Your mission file (already created by `s9 mission start`)

**Location:** `.opencode/work/missions/YYYY-MM-DD.HH:MM:SS.role.persona.codename.md`

**Update throughout your mission, not just at the end!**

### "I'm planning a complex feature"

**Options:**
1. **For task-specific planning:** Add to task notes via `s9 task update`
2. **For epic-level planning:** Update the epic file in `.opencode/work/epics/`
3. **For general brainstorming:** Create a file in `.opencode/work/planning/`

### "I wrote a helpful script that should be permanent"

**Use:** `scripts/` in the project root (NOT `.opencode/work/scripts/`)

**Process:**
1. Refactor and generalize the script
2. Add comprehensive documentation
3. Move from `.opencode/work/scripts/` to `scripts/`
4. Update project documentation

### "I need to document an architecture decision"

**Use:** `.opencode/docs/adrs/`

**Follow the ADR workflow in:** `.opencode/docs/guides/adr-workflow.md`

### "I want to create a guide for other agents"

**Use:** `.opencode/docs/guides/`

**Example:** This file!

## File Lifecycle and Cleanup

### Temporary Files

Files in `.opencode/work/` are often temporary and should be cleaned up:

**When to clean up:**
- Mission ends (clean up your mission-specific scripts)
- Task completes (remove task-specific scripts)
- Work is handed off (ensure handoff docs are complete)
- Scripts are promoted to permanent utilities

**How to clean up:**
- Remove scripts from `.opencode/work/scripts/`
- Archive or delete planning documents
- Ensure mission logs are complete before ending mission

**Don't delete:**
- Mission log files (historical record)
- Task files (managed by system)
- Epic files (until epic complete)
- Handoff files (until accepted)

### Permanent Files

Files in these locations are permanent:
- `.opencode/docs/`
- `.opencode/skills/`
- `.opencode/scripts/`

Only add files here if they provide long-term value.

## Anti-Patterns: What NOT to Do

### ❌ Creating files in project root

**Bad:**
```
./temp-script.py
./notes.md
./TODO.txt
```

**Why it's bad:**
- Pollutes the project structure
- Gets committed to git accidentally
- Confuses other developers
- Mixes work artifacts with project code

**Do instead:**
- Use `.opencode/work/scripts/` for scripts
- Use mission file for notes
- Use task files for TODOs

### ❌ Creating status files anywhere

**Bad:**
```
./STATUS.md
./PROGRESS.txt
.opencode/CURRENT_WORK.md
```

**Why it's bad:**
- Creates confusion about source of truth
- Becomes stale quickly
- Duplicates information in database

**Do instead:**
- Use `s9 task update` to track progress
- Use mission file for status notes
- Use `s9 dashboard` to view status

### ❌ Temporary files in docs/

**Bad:**
```
.opencode/docs/my-notes.md
.opencode/docs/wip-design.md
```

**Why it's bad:**
- Mixes temporary and permanent docs
- Makes it unclear what's authoritative
- Work-in-progress becomes "permanent"

**Do instead:**
- Use `.opencode/work/planning/` for WIP
- Move to docs only when finalized
- Use mission file for personal notes

### ❌ Permanent scripts in work/scripts/

**Bad:**
```
.opencode/work/scripts/database-backup.py  # Used repeatedly!
```

**Why it's bad:**
- May be deleted during cleanup
- Not discoverable by other agents
- Not in path for easy execution

**Do instead:**
- Move to `scripts/` in project root
- Document in project README
- Make executable and well-documented

### ❌ Leaving orphaned scripts

**Bad:**
- Scripts with no header
- Scripts after task completes
- Scripts with unclear purpose

**Why it's bad:**
- No one knows what they do
- Can't be safely deleted
- Clutters workspace

**Do instead:**
- Always include required headers
- Clean up when task/mission ends
- Link to task/mission clearly

## Summary

**The Golden Rules:**

1. ✅ **All work artifacts go in `.opencode/work/`**
2. ✅ **Use mission files as living documents**
3. ✅ **Clean up temporary files when done**
4. ✅ **Link scripts to tasks via naming convention**
5. ❌ **Never create temporary files in project root**
6. ❌ **Never create status files anywhere**
7. ❌ **Don't pollute docs/ with work-in-progress**

**When in doubt:**
- Is it temporary? → `.opencode/work/`
- Is it permanent? → `.opencode/docs/`, `.opencode/scripts/`, or `scripts/`
- Not sure? → Ask in your mission notes and clean up later!
