## Technical Notes

### Design Decisions

1. **Composite Primary Key**: Used (message_id, mission_id) to ensure each mission can only acknowledge a message once
2. **Idempotent Operations**: acknowledge_message() uses INSERT OR UPDATE to allow re-acknowledgement without errors
3. **Scope Checking**: get_unacknowledged_messages() properly handles both 1-on-1 conversations and scoped discussions
4. **Backward Compatibility**: Existing conversation-level view tracking remains unchanged; acknowledgements are additive

### SQL Query Complexity

The get_unacknowledged_messages() query handles three conversation scope types:
- **Conversations**: Direct participant check (participant_1_id or participant_2_id)
- **Role discussions**: Dynamic scope based on mission role
- **Epic discussions**: Dynamic scope based on task assignment (current_mission_id)
