## 1. Overview

The site-nine TUI provides an interactive terminal interface for human operators managing AI agent
orchestration. It launches when `s9` is invoked with no arguments, replacing the current
`no_args_is_help=True` behaviour. Existing CLI subcommands continue to work unchanged via TTY
detection and a `--no-tui` escape hatch.

The TUI is built with [**Textual**](https://textual.textualize.io/) — a Python reactive UI
framework that renders CSS-styled widgets in the terminal, supports async I/O natively, and ships
with first-class keyboard navigation.

## 2. CLI Integration Strategy

### 2.1 Entry-Point Behaviour

Current entry point (`s9 = "site_nine.__main__:app"`) uses Typer with `no_args_is_help=True`.

**Proposed change:** replace the bare-invocation behaviour:

```python
# src/site_nine/__main__.py

@app.callback(invoke_without_command=True)
def main(ctx: typer.Context, no_tui: bool = typer.Option(False, "--no-tui")) -> None:
    """The headquarters for AI agent orchestration"""
    if ctx.invoked_subcommand is None and not no_tui:
        from site_nine.tui.app import SiteNineApp
        SiteNineApp().run()
    elif ctx.invoked_subcommand is None:
        print(ctx.get_help())
```

This preserves 100% backward compatibility:

| Invocation | Behaviour |
|---|---|
| `s9` | Launches TUI |
| `s9 --no-tui` | Prints help (old behaviour) |
| `s9 dashboard` | Runs CLI command as before |
| `s9 task list` | Runs CLI command as before |
| Non-TTY (`s9 \| jq`) | Falls back to help (TTY detection guard) |

### 2.2 TTY Guard

Before launching the TUI, check `sys.stdout.isatty()`. If false (piped output, CI, scripting),
fall through to the help text. This prevents TUI from corrupting stdout when used in scripts.

```python
import sys

if ctx.invoked_subcommand is None and not no_tui and sys.stdout.isatty():
    SiteNineApp().run()
```

### 2.3 Dependency Addition

Textual is not currently a dependency. Add to `pyproject.toml`:

```toml
dependencies = [
    ...
    "textual>=0.80.0",
]
```

Textual's only hard runtime dependencies are `rich` (already present) and `markdown-it-py`. No
conflict with existing deps.

## 5. Layout Architecture

### 5.1 Two-Pane Layout (Recommended)

After evaluating the data shapes, a **2-pane horizontal split** is the right default for every
list-detail screen. The data in site-nine is predominantly record-oriented with associated
markdown files — 2-pane matches this perfectly without the complexity penalty of 3-pane.

```
┌─────────────────────────────────────────────────────────────────┐
│  [s9]  Tasks                                    Sat 02:41  [?] │  ← AppHeader
├────────────────────────┬────────────────────────────────────────┤
│  LIST PANE (40%)       │  PREVIEW PANE (60%)                    │
│                        │                                        │
│  ▶ ENG-C-0238  CRIT   │  # ENG-C-0238                         │
│    ARC-H-0239  HIGH   │  Fix bad default model ID              │
│    OPR-H-0066  HIGH   │                                        │

│    TST-H-0069  HIGH   │  **Priority:** CRITICAL                │
│    ARC-M-0216  MED    │  **Role:** Engineer                    │
│                        │                                        │
│                        │  ## Description                        │
│                        │  The default model ID in              │
│                        │  desk_worker.py and worker_spawn.py   │
│                        │  references an outdated model...      │
│                        │                                        │
```

**Why not 3-pane?**
- Site-nine records are either lists + single markdown files, or simple tabular + detail
- A filter/tree pane would add navigation complexity without meaningful benefit at current scale
- Can be revisited if the epic tree view warrants it (Dashboard screen may use a different layout)

## 7. Component Architecture

### 7.1 Core Widget: `SelectableListPane`

```python
class SelectableListPane(Widget):
    """
    Generic list widget with cursor tracking.
    
    Reactive attributes:
        items: list[Any]         — the data items to render
        cursor_index: int        — currently highlighted row
        filter_text: str         — active filter string
    
    Messages emitted:
        ItemSelected(item)       — cursor moved to item
        ItemActivated(item)      — Enter/Space pressed on item
    """
```

Each screen subclasses this with a custom `render_row(item)` method that returns a Textual
`Text` object with appropriate styling for that entity type.

### 7.2 Core Widget: `MarkdownPreviewPane`

```python
class MarkdownPreviewPane(Widget):
    """
    Scrollable markdown renderer that reacts to SelectableListPane.ItemSelected.
    
    Reactive attributes:
        content: str             — raw markdown content to display
        title: str               — displayed in pane header
    
    Uses Textual's built-in Markdown widget for rendering.
    Loads file content asynchronously to avoid blocking the event loop.
    """
```

### 7.3 Core Widget: `DetailScreen`

```python
class DetailScreen(Screen):
    """
    Full-page detail overlay, pushed onto the Textual screen stack.
    
    Parameters:
        title: str               — header title
        content: str             — markdown content
        file_path: Path | None   — optional file to open in editor
    
    Pops itself on Esc/q. Calls app.suspend() around $EDITOR invocations.
    """
```

### 7.4 `DataLoader`

```python
class DataLoader:
    """
    Async thin wrapper over existing synchronous managers.
    Executes DB calls in a thread pool to keep the TUI responsive.
    
    Methods (all async via asyncio.to_thread):
        async def load_tasks(role, status, epic_id) -> list[Task]
        async def load_missions(active_only) -> list[Mission]
        async def load_messages(mission_id) -> list[Conversation]
        async def load_adrs() -> list[ArchitectureDoc]
        async def load_dashboard() -> FullDashboardData
        async def load_file_content(path: Path) -> str
    """
```

This isolates the TUI from SQLite's threading constraints and keeps the existing synchronous
managers unchanged.

### 7.5 `SiteNineApp`

```python
class SiteNineApp(App):
    """
    Root Textual application.
    
    CSS_PATH = "styles/app.tcss"
    SCREENS = {
        "dashboard": DashboardScreen,
        "missions":  MissionsScreen,
        "messages":  MessagesScreen,
        "tasks":     TasksScreen,
        "adrs":      ADRsScreen,
        "histories": HistoriesScreen,
    }
    BINDINGS = [global keybindings listed in §6.1]
    
    On startup:
        - Detects .opencode dir (raises graceful error if not found)
        - Opens Database connection, instantiates DataLoader
        - Pushes DashboardScreen as initial screen
    """
```

## 8. State Management

Textual's **reactive attributes** (`reactive()`) drive all UI updates. No external state store is
needed.

Each screen holds reactive attributes for its data:

```python
class TasksScreen(Screen):
    tasks: reactive[list[Task]] = reactive([])
    selected_task: reactive[Task | None] = reactive(None)
    filter_text: reactive[str] = reactive("")
    role_filter: reactive[str | None] = reactive(None)
```

When `tasks` changes (after a data refresh), Textual automatically re-renders the affected
widgets. This keeps state local to screens — no shared global state except the `DataLoader`
instance on `SiteNineApp`.

### 8.1 Refresh Strategy

Data is loaded:
- On screen `on_mount()` (initial load)
- On `r` keypress (manual refresh)
- **Not** on a timer — the TUI is for human inspection, not a live dashboard

This keeps the design simple and avoids polling the SQLite database continuously.

Colour variables reference Textual's built-in theme tokens so the TUI respects the user's

## 10. Technical Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Framework | Textual | Modern, async, rich widget set, active development, good keyboard support |
| Pane layout | 2-pane | Site-nine data is list+file; 2-pane matches this without added complexity |
| State management | Textual reactives | Native to framework, no extra deps, sufficient for this use case |
| Data access | `asyncio.to_thread` wrapper | Reuses existing synchronous managers without rewriting them |
| Detail expand | Push `Screen` overlay | Textual idiom; back-navigation is automatic, no custom stack needed |
| Vim motions | `j/k/gg/G` | Consistent with target user base (developers); `hjkl` lateral focus |
| CLI backwards compat | TTY detection + `--no-tui` flag | Zero breakage for scripting/agents/CI |
| Filter UI | Inline `/` prefix | Familiar from `less`/`vim`; no dedicated filter widget needed |
| Editor integration | `app.suspend()` | Textual standard pattern for launching external processes |
| Module location | `src/site_nine/tui/` | Keeps TUI isolated from CLI and business logic layers |

## 12. Open Questions / Risks

| Item | Notes |
|---|---|
| Messages screen complexity | Threading (parent/reply) adds UI complexity; may need accordion or indented list |
| `s9 comms` mnemonic | `g` for messages may confuse; consider `i` for "inbox" or `c` for "comms" |
| Large datasets | 237 tasks today; if task count grows to thousands, virtual scrolling may be needed (Textual's `ListView` virtualises by default — likely fine) |
| Windows terminal support | Textual works on Windows but some terminals have limited ANSI support; out of scope for now |
| Role filter persistence | Should role filter persist across screen switches? Recommend no — simpler, re-filter on each visit |
